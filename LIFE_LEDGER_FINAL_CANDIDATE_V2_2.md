# RUNLU Life Ledger · Final Candidate V2.2

## Status
Final Candidate V2.2 is the first integrated candidate that is intended to use the shared canonical transaction core for all financial math.

File: `life-ledger-final-candidate-v2-2.html`
Core: `life-ledger-core-v2.js` (Core 2.3 or later)

This is still a **staging candidate using fictional sample data only**. It is not connected to the current private Life Ledger dataset.

## What is integrated
- Home with monthly Balance, Income, Expenses.
- Horizontal category spending bars.
- Direct Home entry into Entries or Sheet View.
- Amount-first Quick Add.
- Entries View over the canonical record set.
- Desktop 12-month Sheet View.
- iPhone focused-month Sheet View.
- Grocery / Fuel recurring presentation as either W1–W5 detail or one running total.
- Sheet `Add amount`, `Set visible total`, `Clear visible total safely`, and immediate Undo.
- Monthly Income vs Expense Trends.
- Canonical JSON and CSV export for the isolated sample dataset.

## Financial invariants
1. Sheet corrections stay in the same economic type.
   - Expense corrections remain Expense.
   - Income corrections remain Income.
2. A reduction is represented by a negative `adjustmentDelta`, not by fabricating the opposite economic type.
3. W1–W5 editing is week-scoped.
   - Setting W1 does not change W2–W5.
   - Clearing W2 does not clear the monthly total.
4. Core 2.3 normalizes week-scoped record dates so W5 cannot accidentally land in W4.
5. Running total equals the sum of W1–W5 over the same underlying records.
6. Adjustment records remain visible in Entries as traceable audit records and are not directly edited in the candidate UI.
7. Undo removes only the record generated by the immediately preceding Sheet action.

## Candidate storage isolation
The candidate uses its own sample storage key:

`runlu-life-ledger-final-candidate-v2-2-sample`

It must never attempt to discover, rename, overwrite, or migrate unknown production keys automatically.

## Production release gate
Do not connect the Final Candidate to current private data until all of these are true:

- [ ] Exact current private-app URL/source is identified.
- [ ] Exact current localStorage / IndexedDB keys are inventoried read-only.
- [ ] Existing schema fields and date/amount/type semantics are documented.
- [ ] A full user-controlled export exists before any migration.
- [ ] Migration runs first on a copy, never the live dataset.
- [ ] Record count reconciles.
- [ ] Every month Income reconciles.
- [ ] Every month Expense reconciles.
- [ ] Every month Balance reconciles.
- [ ] Category totals reconcile where categories exist in the old data.
- [ ] No duplicate IDs after migration.
- [ ] No invalid dates / amounts / types after migration.
- [ ] W1–W5 grouping is verified with edge dates 7/8, 14/15, 21/22, 28/29.
- [ ] JSON export → restore round trip is verified.
- [ ] CSV export is verified separately as portability, not as the canonical restore format.
- [ ] iPhone test: Home, Quick Add, Entries edit, W1–W5 edit, running total, Undo.
- [ ] Mac/desktop test: 12-month Sheet, Entries, Trends, export.
- [ ] Old private version remains available as rollback during first migration trial.

## Product boundary
The release candidate must continue to feel like a simple personal ledger, not accounting software. The complexity required for traceability stays underneath the interface.

Product promise:

**One ledger. Two views. Both editable.**

Supporting principle:

**Spreadsheet freedom without spreadsheet work.**
